FixPart.de category structure — final result

How fixpart.de organises more than 20 million spare parts, what our three API shops do differently, and how we would rebuild the same structure in Laravel, PostgreSQL and Meilisearch.

FixPart did not build a bigger category tree. It built a product database with a curated navigation on top.

The wholesaler API supplies the facts: article numbers, brands, device types, compatibility, price and stock. FixPart adds the editorial layer — its own appliance names, 375 part categories, a five-level classification, SEO landing pages and a fit guarantee. That layer is what makes the shop feel curated; it is also the part we have to build ourselves.

1Two axes, not one tree. Customers start with their appliance or with the part. Both paths use the same products.
2Navigation is device-first. 105 appliance groups → 1,511 brands → model / type number, with a separate A–Z part index.
3URLs are a fixed matrix. Appliance × brand × part pages are generated; breadcrumbs come from the URL, not the classification.
4One product, many listings. One classification path per SKU; compatibility links create the many entry points without duplicating products.

02

How the customer moves — and how the page is built

Navigation
Appliance → brand → part → type number

The main entrance is /gerate with 105 appliance groups. People who know the part name use the flat A–Z index at /ersatzteile/{part}.

URLs & breadcrumbs
A fixed matrix of the two axes

/waschmaschine-ersatzteile/bosch/turgummi is the deepest example. The breadcrumb is rebuilt from the URL segments. On a product page it deliberately collapses to the leaf: Home › Tür › product.

Filters
Appliance · brand · type number · part category

Plus price, availability and condition (original / aftermarket / refurbished). The type-number picker on a brand page is the narrowest filter.

One product, many listings
Bosch 00704286 — washing-machine door

One classification path (Mechanisch › Gehäuseteil › Fenster › Tür). Device brands Balay, Bosch, Profilo and Siemens. Appliance type Waschmaschine. 1,802 compatible models. It appears on dozens of appliance × brand × part pages without being copied into 1,802 categories.

Why this matters commercially
One canonical product, many qualified entrances

Price and stock are updated once. There is no duplicate content. The generated landing pages carry the SEO, while the product page stays the source of truth for the customer and for Google.

The difference is editorial: FixPart turns those dimensions into a shop. The other three remain databases — even when they sell the same part. The API provides the facts; the taxonomy is the differentiator.

04

What the API gives us — and what we must add

Provided directly by the wholesaler
  • Article number, MPN and description
  • Supplier part group / part type in supplier wording
  • Device brand(s), device type(s), model / type numbers
  • Compatibility list — the most valuable field
  • Price and stock
What we must add (the moat)
  • 105 normalised appliance groups (one name per device type)
  • 375 part categories + the five-level classification
  • Aliases and synonyms: supplier spelling → our category
  • SEO copy, landing pages, breadcrumbs and sitemaps
  • Fit guarantee and translations for DE / ES / IT

Avoid the trap of the API shops: never model “AEG-Waschmaschine” as a category. Brand and device are separate dimensions, connected to products through compatibility.

05

How we would rebuild it

1

PostgreSQL schema

categories (parent_id + materialised path), brands, models, products, product_model compatibility, seo_landings. The tree is small (~500 rows); compatibility can reach millions.

2

Import pipeline

Stage the raw feed (JSON + hash) → normalise via category aliases → upsert products with one primary category → attach compatibility rows → queue reindex. Nightly full import, idempotent.

3

Meilisearch

One products index: flat category_ids, brand, appliance_types, condition, price, in_stock as filterable facets. A separate models index powers “find by type number”.

4

Storefront

Tree and breadcrumbs from PostgreSQL; filters and counts from Meilisearch. Generate appliance × brand × part pages, but publish only pages with at least three products — otherwise noindex.

Technical detail and working code: migration, importer, indexer and Meilisearch settings are in the separate code archive.

Open questions & assumptions
  • Wholesaler identity. Assumed EURAS-type feed: ersatzteilblitz deep-links to shop.euras.com. Contract and field list to confirm.
  • Product-group path. If the feed contains one, map it 1:1. If not, the 375-node list must be curated.
  • 5,000 vs 375. The gap is classification leaves and generated combinations, not 5,000 public index pages.
  • Brand coverage. 1,511 captured vs 2,000+ claimed; some brands are probably not linked in the A–Z directory.
  • Legal. Build from our own feed and editorial work — not from scraped FixPart content.
