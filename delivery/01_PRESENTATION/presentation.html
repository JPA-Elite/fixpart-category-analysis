Comparison

Same wholesaler data — very different shop

The three API shops publish the supplier’s raw dimensions. FixPart normalises them and adds a curated layer on top.

ShopNavigationDepthOwn taxonomy / editorial layer
ersatzteilblitz.deGerätegruppen A–Z + Artikelgruppen A–Z; inquiries deep-link to shop.euras.com2none supplier dimensions only
wildbihler-shop.deHersteller A–Z + Geräte A–Z; brand × device treated as separate “manufacturers” (e.g. AEG-DAMPFBÜGELEISEN)2–3none brand and device stay raw
ersatzteile-24.comBrand index, brand → device model lists, part pages; a repair assistant at /shop.php3none no renamed groups or part taxonomy

Identical in all four: part brand, device brand, device type, model / type number, article number, description and compatibility all come from the same supplier dimensions.
The difference is editorial: FixPart turns dimensions into a shop. The others stay databases — even when the underlying articles are the same.

Our starting point: we already have the same dimensions. What we lack is the 375-node part taxonomy and the generated landing pages — both are buildable on top of the feed.

What we get, what we build

The API gives us the facts. The taxonomy is our work.

Provided directly by the wholesaler API
  • ✓Article number, MPN and description
  • ✓Supplier part group / part type in supplier wording
  • ✓Device brand(s), device type(s), model / type numbers
  • ✓Compatibility list (the most valuable field)
  • ✓Price and stock
What we must add (the moat)
  • +105 normalised appliance groups (one name per device type)
  • +375 part categories + 5-level classification
  • +Aliases and synonyms (supplier spelling → our category)
  • +SEO copy, landing pages, breadcrumbs, sitemaps
  • +Fit guarantee, translations for DE / ES / IT

Avoid the trap of the API shops: never model “AEG-Waschmaschine” as a category. Brand and device are separate dimensions, connected to products through compatibility.

Budget the taxonomy

The import is commodity work. The curated categories and aliases are the differentiator.

Curate once, reuse

One taxonomy serves DE, ES and IT; only labels and copy need translating.

The SEO follows

Once the two axes are clean, landing pages are generated, not hand-built.

The rebuild

One import pipeline, two databases, one storefront

PostgreSQL owns the hierarchy and the truth. Meilisearch owns search, facets and the type-number finder.

Source
Wholesaler API
Articles, brands, device types, compatibility, price, stock
›
Step 1
Staging
Raw JSON + hash, so every re-import is idempotent and debuggable
›
Step 2
Normaliser
Supplier spelling → our brand, appliance and part category
›
Step 3
PostgreSQL
categories · brands · models · products · compatibility · SEO landings
›
Step 4
Meilisearch
One product index with facets; separate model index
›
Step 5
Storefront
Category pages, search, breadcrumbs, type-number finder
Category table: adjacency list (parent_id) plus a materialised dot path. A subtree is one indexed LIKE 'mechanisch.gehaeuseteil.%' — no recursive query per request.
Search index: flat category_ids, brand, appliance_types, condition, price, in_stock as filterable facets. The tree and breadcrumbs stay in Postgres.

Scale: ~500 category rows (105 appliance + 375 part + intermediate levels) — small enough to cache in Redis. The compatibility table can reach millions of rows.

Rule: a product gets one primary category from the feed. Appliance and brand listings are driven by compatibility, never by extra category assignments.

Delivery plan

Start with the catalogue, then add the SEO surface

Weeks 1–3
Taxonomy + import

105 appliances, 375 part categories, aliases, nightly import, product & compatibility tables, canonical product pages.

Weeks 4–6
Navigation + search

Appliance → brand → part pages, Meilisearch facets, type-number finder, breadcrumbs, filters.

Weeks 7–10
SEO landings

Generated appliance × brand × part pages, sitemaps, internal linking. Publish only pages with ≥ 3 products, otherwise noindex.

Ongoing
Expansion

DE → ES / IT translations, synonym tuning, zero-result monitoring, price/stock freshness.

Indicative effort for one senior developer; actual timing depends on the feed contract and catalogue size.

Decisions we need from the business

  • Wholesaler contract and field list — does the feed already contain a product-group path?
  • If not: who owns the 375-node taxonomy and the 5-level classification?
  • Which market launches first — and do we translate categories or only products?
  • Minimum assortment per landing page before it is indexable?

Assumptions

EURAS-type feed (ersatzteilblitz deep-links to shop.euras.com). Brand count 1,511 captured vs 2,000+ claimed. “5,000+ categories” = classification leaves + generated combinations, not 5,000 index pages. Build from our own feed and editorial work — not scraped FixPart content.
